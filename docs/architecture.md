# โครงสร้าง HDC Tote tracker

## หน้าจอ

- `/`: ระบุชื่อผู้ปฏิบัติงาน และเข้าสู่ระบบ Admin
- `/scan`: รับ QR, ลงทะเบียนรหัสใหม่, ดูสถานะ/Store/ประวัติ, จัดการรูป, ตรวจสอบและยืนยันสถานะ
- `/dashboard`: จำนวน Tote ตามสถานะ ค้นหารหัส กรองสถานะ และเปิด Tote โดยตรง แบ่งหน้า 30 รายการ
- `/admin/login`: เข้าสู่ระบบผู้ดูแล
- `/admin/stores`: เพิ่ม/แก้ไข/เปิดปิด/ลบ Store และค้นหา/ลบ Tote เฉพาะผู้ดูแล ต้องพิมพ์ข้อความยืนยันก่อนลบ

## หลักข้อมูล

`totes.code` เป็น Primary key คงเดิมตลอดอายุ Tote เช่น HDC000001 ไม่สร้างเลขใหม่ตอนรับกลับ และไม่สร้าง QR ในเวอร์ชันนี้

รหัสเป็น `HDC` ตามด้วยตัวเลขอย่างน้อย 1 หลัก ไม่ล็อก 6 หลัก ความยาวรวมสูงสุด 100 ตัวอักษร Migration 002 ปรับ constraint โดยคงข้อมูลเดิม ชื่อผู้ปฏิบัติงานไม่ซ้ำเมื่อเทียบแบบไม่สนตัวพิมพ์ใหญ่เล็กและช่องว่างหัวท้าย; migration รวม session ที่ชี้ชื่อซ้ำไปยังข้อมูลคนเดียวกันก่อนสร้าง unique index รายชื่อเดิมค้นหาได้เมื่อพิมพ์อย่างน้อย 3 ตัวอักษรในหน้าเข้าสู่ระบบ

การลบ Store ตั้ง `deleted_at` และปิดใช้งาน เพื่อนำออกจากรายการโดยคง foreign key ของ Tote ที่ยังอยู่ Store รวมถึงประวัติเดิม การเพิ่มรหัส Store เดิมอีกครั้งคืนรายการได้ การลบ Tote เป็นการลบจริงทั้งรูปและ event โดยล็อก Tote ก่อนดำเนินการ Endpoint ลบทั้งสองรับ JSON `confirmation` เท่ากับ `DELETE {code}` และตรวจสิทธิ์ Admin ฝั่ง server

| Action | จาก | ไป | Store ปัจจุบัน |
| --- | --- | --- | --- |
| REGISTER | ไม่มี | READY | ว่าง |
| DISPATCH | READY | AT_STORE | Store ที่ผู้ใช้เลือก |
| RETURN | AT_STORE | RETURNED | คง Store เดิมให้ตรวจสอบ |
| RESET | RETURNED | READY | ล้างปลายทาง |

`tote_events` เก็บ action, สถานะก่อน/หลัง, snapshot รหัสและชื่อ Store, ชื่อผู้บันทึก, เวลา, หมายเหตุ การแก้ชื่อหรือปิด Store ภายหลังไม่เปลี่ยนข้อความในประวัติ ไม่ลบประวัติเมื่อ RESET

`photos` อยู่ฐานภาพทั้ง metadata และ binary ใช้ unique `(tote_code,slot)` และ CHECK `slot BETWEEN 1 AND 6` เพื่อจำกัด 6 รูปที่ฐานข้อมูลโดยตรง ไม่ผูกภาพเข้ากับ event: เป็นชุดภาพปัจจุบันของ Tote ไม่ใช่อัลบั้มย้อนหลังแต่ละรอบ การลบรูปเมื่อ READY เป็นการลบจริง

## ความสอดคล้องของข้อมูล

- ล็อกแถว Tote ด้วย `FOR UPDATE` ก่อนเปลี่ยนสถานะหรือแก้รูป
- การเปลี่ยนสถานะรับ `expected_version` ป้องกันสถานะเก่าจากอีก Handheld
- การแก้รูปตรวจ version ป้องกันคำขอจากรอบก่อนหน้าหลังรับกลับ/ล้างค่าแล้ว
- รูปช่องเดิมที่ hash ตรงกันถือเป็น retry และไม่เปลี่ยน ID ส่วนภาพต่างกันในช่องที่มีรูปแล้วจะถูกปฏิเสธ ไม่เขียนทับรูปอีกเครื่อง
- การลบรูปต้องส่ง expected_photo_id เพื่อไม่ลบภาพใหม่ที่มาแทนช่องเดิม
- `request_id` ของการเปลี่ยนสถานะรองรับส่งซ้ำคำขอเดิมหลังเน็ตหลุด โดยไม่สร้าง event ซ้ำ; คำขอ ID เดิมแต่ payload ต่างกันจะถูกปฏิเสธ
- Advisory lock ของ request_id ป้องกันคำขอ ID เดียวกันจากหลาย Tote แข่งกัน insert แล้วกลายเป็น server error
- สถานะและ event อยู่ transaction เดียวกัน ส่วนภาพอยู่ transaction ของฐานภาพ ไม่มี distributed transaction ภาพ commit ก่อนปล่อยล็อก Tote และไม่แก้ข้อมูลสถานะใน transaction นั้น
- การลบ Tote บันทึกคิว photo_cleanup_jobs พร้อมลบ metadata ใน transaction เดียวกัน จากนั้นลบภาพและลองใหม่ทุก 60 วินาทีเมื่อฐานภาพขัดข้อง GET รูปตรวจว่า Tote ยังอยู่ก่อนส่งภาพ การลงทะเบียนรหัสเดิมรอให้ cleanup ของรอบก่อนสำเร็จ
- รายการและยอดนับของ Dashboard อ่านจาก snapshot เดียวกัน และ detail ใช้ shared lock ระหว่างอ่านสถานะ/ประวัติ/รายการรูป
- ชื่อ Store และผู้บันทึกใน history เป็น snapshot; ประวัติเรียงใหม่ไปเก่า

## API หลัก

| Method | Path | การทำงาน |
| --- | --- | --- |
| POST | `/api/worker/session` | เริ่ม session ด้วยชื่อผู้ปฏิบัติงาน |
| GET | `/api/workers/suggestions?q=...` | รายชื่อเดิมที่มีข้อความตรงกัน ตั้งแต่ 3 ตัวอักษร (ก่อนเข้าสู่ระบบ) |
| GET | `/api/worker/me` | ผู้ปฏิบัติงานปัจจุบัน |
| GET | `/api/stores` | Store ที่เปิดใช้งาน |
| POST | `/api/totes` | ลงทะเบียนรหัส Tote; เรียกซ้ำไม่เพิ่มประวัติ |
| GET | `/api/totes?q=&status=&page=1` | ค้นหาและนับตามสถานะ |
| GET | `/api/totes/{code}` | สถานะ + ประวัติ + รายการรูป |
| POST | `/api/totes/{code}/transitions` | เปลี่ยนสถานะพร้อม version/request ID |
| PUT | `/api/totes/{code}/photos/{slot}?expected_version=N` | บันทึกรูป multipart `file` เฉพาะ READY |
| GET | `/api/totes/{code}/photos/{slot}` | อ่าน JPEG |
| DELETE | `/api/totes/{code}/photos/{slot}?expected_version=N&expected_photo_id=UUID` | ลบรูปเฉพาะ READY และรูป ID เดิม |
| POST | `/api/admin/login` | เข้าสู่ระบบผู้ดูแล |
| POST | `/api/admin/logout` | ออกจากระบบผู้ดูแล |
| GET / PUT | `/api/admin/stores`, `/api/admin/stores/{code}` | รายการทั้งหมด / บันทึก Store |
| DELETE | `/api/admin/stores/{code}` | ลบ Store ออกจากรายการ พร้อมข้อความยืนยัน |
| DELETE | `/api/admin/totes/{code}` | ลบ Tote / ประวัติ / รูป พร้อมข้อความยืนยัน |
| GET | `/api/ready` | ตรวจการเชื่อมต่อฐานข้อมูลทั้งสอง |

## สิ่งที่ต้องยืนยันในการทดสอบหน้างาน

ใช้รหัสรูปแบบ HDC + ตัวเลขไม่จำกัดที่ 6 หลัก, รูปไม่บังคับก่อนส่ง, รับกลับแล้วต้องยืนยันล้างปลายทางแยกขั้นตอน, รูป 6 ช่องต่อ Tote ทั้งหมดและไม่เก็บรูปเก่าย้อนหลังหลังลบ เหล่านี้เป็นค่าเริ่มต้นของโครงรุ่นนี้และปรับได้เมื่อได้ workflow จริง

ยังไม่มีการจอง Tote, ส่งเป็น batch, export, offline sync, Archive, ระบบสร้าง/พิมพ์ QR และการยืนยันตัวบุคคลของพนักงาน
